# Git 運用ルール（ブランチ・リリース）

このプロジェクトの Git 運用の正典。開発者（人）と Claude の両方がこれに従う。

## 1. ブランチの役割

```
main ──────────●───────────────●────────  リリース版のみ。タグ付き・確実に動く状態
              ↑ v0.1.0         ↑ v0.2.0    (オーナーの指示でのみ更新)
develop ──●──●──●──●──●──●──●──●──●──  日々の開発の本流(統合先)
           \    /     \      /
  feature/xxx ●●   fix/yyy ●●             develop から切り、終わったら develop へ
```

| ブランチ | 役割 | 誰が更新するか |
|---|---|---|
| `main` | **リリース専用**。バージョンタグ付きで「確実に動く版」だけを置く | オーナーの指示があったときのみ（Claude はリリース作業を行うが、指示なしに main を触らない） |
| `develop` | 開発の本流。機能・修正はすべてここに集まる | Claude も自由に操作してよい。オーナーが随時確認する |
| `feature/<内容>` | 機能追加の作業ブランチ。**develop から切る** | 作業者 |
| `fix/<内容>` | バグ修正の作業ブランチ。**develop から切る** | 作業者 |
| `claude/<内容>` | クラウドの Claude セッション用の作業ブランチ。扱いは feature/fix と同じ | Claude |

- 作業ブランチは**短命**にする（1ブランチ＝1テーマ、数日以内に develop へ取り込む）。
- 取り込みは **PR（feature/fix → develop）** で行う。差分と説明が記録に残り、あとからオーナーが確認できる。Claude は develop への PR を自分でマージしてよい。
- 取り込み済みの作業ブランチは削除する。

## 2. リリース（develop → main）

オーナーの指示で行う。手順:

1. develop で Unity を開き、**タイトル → ワールドマップ → キャラ選択 → バトル → リザルト** を通しで確認する。
2. リリース前チェック: デバッグ用機能（即死カード・Esc でデバッグ室・デバッグ表示など）が通常プレイで無効になっていること。
3. PR（develop → main）を作り、オーナーがマージする。
4. main の取り込みコミットに**バージョンタグ**を付ける: `v<メジャー>.<マイナー>.<パッチ>`（例 `v0.1.0`）。
   - マイナー: 遊べる範囲が広がった（例: ステージ2まで一巡）
   - パッチ: リリース後の不具合修正のみ
5. リリース後に main で緊急修正が必要になったら、`fix/xxx` を main から切って main と develop の両方に取り込む。

## 3. コミットの単位

- **1コミット＝1つの変更理由**。「〇〇追加＋△△修正＋既存作業も同梱」のようにまとめない（どの変更でバグが入ったか追えなくなる）。
- コミットメッセージは「何をしたか」を1行目に、必要なら空行の後に理由を書く（日本語でよい）。
- `.meta` ファイルは対応するファイルと**必ずセットで**コミットする。

## 4. Unity 特有の注意

- **同じシーン/プレハブを複数ブランチで同時に編集しない**（YAML の衝突は手で解消しにくい）。どうしても必要なら Unity の Smart Merge（UnityYAMLMerge）を設定する。
- `Library/` `Temp/` `Logs/` `UserSettings/` などは `.gitignore` 済み。OS のゴミファイル（`.DS_Store` 等）もコミットしない。
- 画像・音声などの大きな素材が増えてきたら Git LFS の導入を検討する。

## 5. GitHub 側の設定（オーナーが行う）

- `main` のブランチ保護: Settings → Branches → Add branch ruleset で `main` を対象にし、
  「Require a pull request before merging」と「Block force pushes」を有効にする。
- 必要に応じて `develop` にも「Block force pushes」を設定する。
